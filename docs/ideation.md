# Ideation: help the problem-solvers finish

## Observation

Hackathon teams face their own coordination problem while solving another problem. Beginners need a role; builders need a feasible scope; presenters need time; organisers need accessible, complete submissions.

These are product hypotheses, informed by the founder's conversations and event participation. They are not quantified findings from a formal study.

## Audience and job

For a first-time participant like Vishnu: understand where to contribute and complete a useful first task.

For a team: agree on one feasible workflow, distribute work, recover from blockers, and deliver all organiser-required items before the deadline.

## Product proposition

From first arrival to a judge-ready submission, with a clear next action at each stage.

## Smallest complete journey

Read confirmed event requirements → define one user and problem → assign tasks → build one end-to-end workflow → test → rehearse → verify and submit.

## Differentiation to validate

Delivery is planned alongside the build. Scope Rescue protects the core demo when time is short. Beginner guidance connects non-coding roles to practical work.

## Validation plan

Observe five beginners and one real team using the app without founder explanation. Measure time to identify a first task, ability to state completion conditions, missing deliverables, and submission completion. Interview an organiser about checklist accuracy. Compare against the team's normal process without inventing causal savings from a single trial.
